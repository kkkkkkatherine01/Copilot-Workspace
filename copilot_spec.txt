# 客服 Copilot 工作台 — 项目 Spec（给 Claude Code）

## 一、项目背景

构建一个电商客服 Copilot 工作台：客服与用户对话时，系统根据用户消息从 FAQ 知识库中检索相关内容，调用 LLM 生成回复建议，客服可编辑、采纳或忽略建议，编辑后的回复作为正式回复发送给用户，客服的处理结果（采纳/修改/忽略）记录到反馈日志，形成闭环。

## 二、技术栈（请严格按此实现，不要自行更换）

- 应用框架：**前后端分离**
  - 后端：FastAPI（Python），提供 REST API
  - 前端：React（Vite 脚手架，纯 React + 简单 CSS，不引入 UI 组件库）
- 检索：本地向量检索，embedding 模型使用 `shibing624/text2vec-base-chinese`（中文优化，本地推理，不调用外部 API），相似度计算用 cosine similarity，FAQ 数据量小（30条），无需引入 FAISS 等向量数据库，直接用 numpy 暴力计算距离即可。FAQ 向量在服务启动时预计算一次并缓存在内存中，不要每次请求都重新编码全部 FAQ。
- 生成：Anthropic Claude API（使用 Claude Haiku 模型，我会提供 API Key，通过环境变量 `ANTHROPIC_API_KEY` 读取）
- 数据存储：SQLite，用于存储反馈日志。对话历史本轮不做持久化，由前端 state 维护即可（demo 场景，刷新页面丢失属于可接受范围，README 中需说明这个取舍）
- 语言：后端 Python，前端 JavaScript/JSX

## 三、核心设计原则（务必在代码结构和 README 中体现）

LLM 只负责"生成建议"，不直接执行任何对用户产生影响的动作。采纳、编辑、发送这些动作必须经过客服（人类）的确认才会生效。程序对每一次人工决策（采纳/修改/忽略）都要留痕记录，不允许 LLM 自动发送任何回复。

## 四、系统架构与数据流

```
用户消息输入（前端）
   ↓ POST /api/suggest
后端 检索模块：将用户消息编码为向量，与 FAQ 库中每条 FAQ 的向量计算 cosine similarity，
         取相似度最高的 top-3 条 FAQ，同时记录最高相似度分数作为置信度参考
   ↓
后端 生成模块：将「用户消息 + 检索到的 top-3 FAQ 内容」组装进 prompt，调用 Claude API
         生成回复建议。prompt 中必须包含以下约束：
         1. 只能基于检索到的 FAQ 内容回答，不能编造 FAQ 中没有的信息
         2. 明确标注本次回复参考了哪条/哪些 FAQ 的 id（用于前端做知识溯源展示）
         3. 如果检索到的 FAQ 相似度都很低（低于阈值，比如 0.5），要在回复中提示
            "未找到明确匹配的知识条目，建议人工核实"，而不是强行编造答案
   ↓ 返回 JSON：{ suggestion, retrieved_faqs: [{id, question, answer, score}], confidence, message_id }
前端展示：
   左侧：用户消息对话流（可从下拉框加载一个测试会话 test_conversations.json 中的场景）
   右侧：Copilot 建议面板，展示：
         - 生成的回复建议（可编辑的 textarea）
         - 引用来源：本次建议引用了哪条/哪些 FAQ（展示 FAQ 原文，方便核对）
         - 置信度：用检索到的最高相似度分数展示为百分比或高/中/低标签，
           低于阈值时用醒目样式提示"低置信度，请谨慎核实"
         - 三个操作按钮：采纳（直接使用建议内容发送）、编辑后发送（客服修改文本框内容后发送）、
           忽略（不采纳，客服自己另外处理，标记为忽略）
   ↓ 点击按钮后 POST /api/feedback
后端：将最终发送内容和处理结果（采纳/编辑/忽略）写入 SQLite 反馈日志，返回成功
   ↓
前端：将最终回复追加到左侧对话流中展示（前端 state，不落库）
```

## 五、API 设计

### 5.1 GET /api/conversations
返回 `test_conversations.json` 中的会话列表（conversation_id、第一条用户消息摘要），供前端下拉框选择加载。

### 5.2 GET /api/conversations/{conversation_id}
返回该会话的完整 messages。

### 5.3 POST /api/suggest
请求体：`{ conversation_id, user_message }`
响应体：`{ message_id, suggestion, retrieved_faqs: [{id, category, question, answer, score}], confidence, low_confidence: bool }`

### 5.4 POST /api/feedback
请求体：`{ conversation_id, message_id, user_message, retrieved_faq_ids, confidence_score, suggestion, final_reply, action }`（action 为 "采纳"/"编辑"/"忽略" 三选一）
响应体：`{ success: true }`，同时写入 SQLite `feedback_log` 表

CORS：后端需允许前端开发地址（`http://localhost:5173`）以及部署后的 Vercel 域名跨域访问。

## 六、数据模型

### 6.1 FAQ 知识库（faq.json）

已提供，共 30 条，覆盖 7 个分类（退换货、物流配送、优惠促销、账户安全、支付问题、发票问题、会员权益）。字段结构：
`id`（faq_001 ~ faq_030）、`category`、`question`、`answer`、`keywords`。
直接读取该文件构建向量索引，不要修改其内容。

### 6.2 测试对话数据（test_conversations.json，已提供，共5段，用于验证）

共 5 段，字段：`conversation_id`、`messages`（role/content）、`expected_faq_id`、`difficulty`。用于 (1) 前端下拉框加载演示场景 (2) eval.py 验证检索准确率。

### 6.3 反馈日志表结构（SQLite）

```
feedback_log 表：
- id (主键，自增)
- conversation_id (对应对话)
- message_id (对应用户消息，应用层生成，如 conversation_id + 序号)
- user_message (用户原始消息)
- retrieved_faq_ids (检索到的 FAQ id 列表，JSON 字符串)
- confidence_score (置信度分数)
- suggestion (LLM 生成的原始建议)
- final_reply (客服最终发送的内容)
- action (采纳/编辑/忽略 三选一)
- timestamp (时间戳)
```

## 八、必须完成的核心功能（对照原题目要求）

1. 对话界面：左侧用户消息流，右侧 Copilot 建议面板 —— React 组件左右分栏布局
2. 检索-生成链路：根据用户消息从 FAQ 库检索相关内容，调用 Claude API 生成回复建议

## 十、部署

- 后端：部署到 **Railway**（不用 Render）。原因：Render 免费层是 ephemeral filesystem，
  服务休眠/重启/重新部署时会清空 SQLite 文件，直接导致"反馈闭环"的数据在评审时被清空；
  Railway 免费 Trial（1GB RAM、无自动休眠）没有这个问题，且内存对
  text2vec-base-chinese + torch 更宽裕。
  - 环境变量 `ANTHROPIC_API_KEY` 在 Railway 项目的环境变量设置里配置
  - 挂载一个 Railway Persistent Volume（比如挂到 `/data`），SQLite 文件路径通过环境变量
    `DB_PATH` 配置（本地开发默认是 `./feedback.db`，生产环境指向 `/data/feedback.db`），
    db.py 读取 `os.environ.get("DB_PATH", "./feedback.db")`，不要硬编码路径
  - 已知限制（写入 README）：Railway 免费 Trial 是 30天/$5 额度，用完后降级为
    每月 $1 额度的免费计划，可能不够支撑一个常驻 1GB 服务。这个方案是为"1天完成的
    面试题 + 评审窗口内可访问"这个场景服务的，不是生产级长期方案，如果需要长期跑，
    应该升级 Railway 付费或换成 Render + 独立的免费 Postgres（如 Neon/Supabase）
    做数据持久化。
- 前端：部署到 Vercel，构建产物指向后端部署后的 API 地址（用前端环境变量
  `VITE_API_BASE_URL` 配置，不要硬编码）
- README 中需写明两个服务各自的部署步骤、最终访问链接，以及上面这条 Trial 期限的已知限制
